# User activity — 0.14.0 TST validation

Validated on 2026-10-08 for TST feature delivery. This does not freeze or promote the full 0.14.0 release candidate.

## Behavior and storage

- User activity is available under administration and mobile More; the platform dashboard also links to it. Organization admins are restricted server-side to their home organization, regardless of submitted filters. Platform admins can view all organizations without requiring a home organization or Support View.
- One `UserActivityDay` record exists per user/UTC date. It contains only user ID, organization ID, date, first activity time, latest login time, and an integer login count. The composite primary key avoids a separate event ID. Two compact indexes support date and tenant/date filtering. No IP, user agent, page path, device identifier, JSON payload, or session credential is stored.
- Successful password sign-in creates the session and increments its daily login count in one database transaction. Failed authentication does not call session creation and does not contribute activity. Repeated sign-ins aggregate rather than create separate event rows; the UI labels these as daily history and shows the latest login time, not a complete timestamp list of every login.
- Foreground page navigation, focus/visibility return, pointer, keyboard, and scroll interaction record usage even when an existing session stays signed in. An idle open tab and existing background appearance/calendar/API refreshes do not manufacture active days. The client skips a day after successful recording and throttles failed attempts; the database deduplicates across tabs/devices. No heartbeat timer or mutation to general session reads is added.
- Client writes require a same-origin POST and an active authenticated session. The server supplies the user, organization, activity kind, and UTC date. Submitted identity, organization, login flag, or date is ignored. Successful login auditing also counts an active day.
- Platform Support View never attributes platform-admin usage to the viewed customer. The organization is the user's home organization when the daily record is first created. Changing membership later does not rewrite historical ownership. Unaffiliated platform users appear under No organization.
- History has no scheduled purge and no foreign-key cascade to users, organizations, or sessions. Deactivation/sign-out/password reset do not erase it. Names/email are joined from current records instead of duplicated in the audit table; deleted records retain their scalar IDs with Deleted user/organization labels. Deleted-user names cannot be reconstructed from this table.
- A sample daily row measured **108 bytes** with PostgreSQL `pg_column_size`; this is the row datum, not total disk usage. Indexes, alignment, page free space, and MVCC add overhead. Growth is bounded to one row per active user/day, independent of clicks/page views/sign-ins. Do not treat the measurement as a guaranteed physical storage cost.
- Default view covers 30 UTC dates. Search updates live using the shared `LiveFilterForm`; date range and activity filters apply to summaries/history. History supports newest/oldest/most-logins sorting and stable user-ID tie breaks with 50-row pagination. Summary cards include organizations without matching recorded activity. Active-days average explicitly uses active users; it is not workforce participation, duration, or work completed. Before deployment history is unavailable.

## Verification

- Full automated suite: **571 tests passed**. Focused tests cover UTC rollover/date validation, admin-only access, rejection of widened tenant scope, platform scope, date defaults/reversal/pagination, usage deduplication, login aggregation, and parameterized report queries. Navigation tests cover platform admins without an organization and exclusion of ordinary users.
- TypeScript, optimized Next.js build, whitespace checks, and repository release comparison pass on the isolated clean-source worktree.
- Real SQL integration on `neon-neat-tst` verifies usage deduplication, login increments, UTC rollover, tenant isolation even with an alternate organization filter, global and filtered platform reports, date/search/login filters, sorting, pagination bounds, and organization summaries. Test writes ran in an explicitly rolled-back transaction; no QA history, users, or sessions persisted.
- The actual POST route was executed with local authentication/database mocks. Cross-origin/missing-origin requests return 403, unauthenticated requests return 401, forged user/organization/login fields cannot override server identity or increment login counts, and responses are private/no-store.
- Real-browser static previews use exact page markup and application CSS at **390 x 844** and **1440 x 900**, in light/dark themes, for populated/empty/loading/error states. No unintended document overflow. Screenshots were visually reviewed; long email addresses wrap and desktop rows retain comparison columns. Pagination's first-page Previous control is explicitly unavailable.
- The real bundled client tracker was browser-tested for initial foreground usage, retry after a 503 response, same-day suppression, idle/hidden exclusion, and next-UTC-day visibility return. The 503 browser console entry was deliberately injected for retry verification.
- Admin data reads/query behavior were validated directly and through local fixtures. No temporary authenticated admin session was created in shared TST; this validation does not claim a live authenticated browser test of the deployed admin page. The shared live-filter implementation is reused.
- React review: server-side authorization precedes data reads, queries run in parallel where independent, history is paginated, browser event listeners clean up on navigation/unmount, and no new client dependency or background polling is introduced.
