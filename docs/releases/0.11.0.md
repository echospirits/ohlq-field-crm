# Neat 0.11.0 — Direct Bailment dashboard reporting

Status: **production candidate; live release gates pending**. This release selectively integrates the accepted native Bailment reporting implementation into production base `f71a71c7f162832bf05afa842b282e947f4dea18` (0.10.2). Production deployment and replacement of the existing dashboard's Bailment connection are not yet claimed. See [validation](0.11.0-validation.md), [checklist](0.11.0-checklist.md) and the [operator guide](../engineering/bailment-reporting.md).

## New

- The existing native Bailment PO and Invoice download supplies a typed Neon reporting snapshot that Looker Studio can read directly, removing the Bailment spreadsheet upload from the regular refresh path once activated.
- Sales Stats gains a week-to-date Bailment total and last week's Bailment total, using Monday–Sunday weeks.
- Core Revenue and Sales Stats show the actual Bailment source acquisition time in Eastern time.

## Improved

- Financial reporting retains the complete native invoice-line source independently of forecasting normalization, exclusions and failures. Existing dashboard brand exclusions and financial-date meanings remain explicit in the report.
- Atomic publication, source provenance, replay protection and bounded retention preserve the last complete snapshot during an unsuccessful refresh.
- The daily load's final persisted-data check also verifies the required reporting snapshot, so successful forecasting cannot conceal a failed financial publication.

## Technical manifest

The candidate contains the tested downloader provenance seam, native CSV parser, financial publisher, source-workflow/refresh outcome integration, additive reporting models/migration, their behavioral tests, the production readiness integration, version metadata and release documentation. Runtime source was selectively taken from TST `00c6e9c5a99136147489838a0b724466ad8e3b7d`; the later readiness correction is validated separately before promotion.

Production workflow schedules, `vercel.json`, dependency graph, application UI, existing provider configuration and unrelated production behavior are preserved. The existing report identity and other spreadsheet datasets remain in place. TST-only retained-archive setup/seed tools, canceled archive models, Tasting Management and other unrelated pilots are excluded; TST remains `0.10.0-dev` with its existing disabled daily schedules. Historical releases and refs are preserved.

The migration is additive and requires no forecast/source backfill. Production is seeded through a real native production acquisition after migration and deployment, not by copying TST financial data. A dedicated restricted reporting login and SSL dashboard connection are provisioned separately. Completion depends on exact-candidate Node 22/npm 10 CI, production-derived migration rehearsal, deployed health, native publication and original-dashboard reconciliation recorded in the checklist.
