# Dark mode — 0.14.0 TST validation

Validated on 2026-10-01. This is feature validation in TST, not production promotion or a full WCAG conformance audit.

## Behavior and research decisions

- Profile & preferences starts with Appearance. The labeled, keyboard-operable Dark mode switch saves immediately and reports saving, saved, and error states. Failed saves retain the last confirmed setting. Light mode remains the default; an explicit account preference takes priority over individual device preferences.
- `User.darkMode` is the durable source of truth, independent of browser storage, device, tenant branding, and session. The root layout reads it through the authenticated user and renders `data-theme` on the initial HTML. No client-only theme lookup or new theme dependency is required.
- Other visible sessions check the server every minute, on window focus, and on visibility changes. Background tabs skip polling. Network failures preserve the last confirmed preference. Requests are uncached, aborted when superseded, and cleaned up on unmount.
- The app uses dark neutral surfaces and lighter status/link colors instead of inverting the screen. Legacy fixed colors now use semantic dark tokens with their exact existing light colors retained as fallbacks. Photos, user-defined tag swatches, document output, and email previews preserve their intended colors. Dark links use an accessible palette independent of arbitrary tenant brand colors.
- [WCAG text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) informed the minimum 4.5:1 target for normal text. [WCAG non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) informed the 3:1 target for input boundaries, switch indicators, and keyboard focus. Status labels and On/Off text accompany color.
- CSS [color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme) gives native controls and scrollbars the appropriate dark appearance. Theme changes introduce no animation or image filter.
- Taster users can access Profile from mobile navigation and edit their personal appearance preference. Their unavailable Calendar settings link is hidden.

## Completed verification

- Full automated suite: **563 tests passed**. Preference validation rejects non-boolean values, writes only the authenticated user's ID, preserves other fields and users, and supports repeated saves and turning off.
- Palette regression tests verify normal text, muted text, links, action states, six semantic status palettes, input boundaries, and focus contrast.
- Clean-source TypeScript check and optimized Next.js build passed. The snapshot contains the feature files and current committed baseline, excludes unrelated untracked files, and uses development resource labels with external side effects disabled. A root-checkout typecheck encounters a pre-existing missing `state` property in the untracked `tmp/ohlq-load-audit-20260928/reproduce-conflict.ts`; that audit script was preserved.
- Real Chrome checks at **390 x 844** and **1440 x 900** covered Profile, Pipeline, Log Visit, Analytics, and My Schedule. No unintended horizontal document scrolling. Profile was visually reviewed in both themes and the final switch is above the contact/password form.
- Real-browser checks covered pending/disabled, success, network/server-error recovery, keyboard focus, reload, turning off, server-rendered dark HTML, independent browser contexts, focus synchronization, and unchanged appearance for another user.
- A fresh authenticated session inherited the saved account preference. A separate taster QA user verified mobile Profile access, visibility synchronization, and minute-based synchronization using Playwright's clock.
- Computed text-contrast checks on the rendered dark Profile, Pipeline, Analytics, and Log Visit pages found no failures against normal/large-text thresholds. These checks supplement the palette tests and visual review; they do not certify every possible data state or operating system.
- API checks confirmed unauthenticated reads/writes fail, invalid payloads return 400, cross-origin writes return 403, and a submitted alternate user ID cannot change another user's preference.
- `git diff --check` and the repository release comparison passed. Temporary QA identities use the isolated TST database and are removed after deployment checks; no real user's preference is changed.

## Migration and release boundary

- Additive migration: `prisma/migrations/20261001120000_user_dark_mode/migration.sql` adds a non-null boolean defaulting to false. No backfill, feature flag, environment variable, or new package.
- Refreshed Vercel configuration identified the `neat-tst` project and verified `APP_ENV=test`, `DATABASE_TARGET_ID=neon-neat-tst`, and the configured expected database hostname before mutation.
- Only the new appearance migration was deployed through Prisma using an isolated migration directory. The existing `PasswordResetToken` table is present, but its `20260923123000_password_reset_tokens` migration is absent from the applied ledger. This pre-existing gap was left unchanged; a normal full-directory migration deploy would attempt that older migration and needs separate reconciliation before production release.
- Deploy only to the dedicated `staging` remote (`echospirits/neat-tst`), branch `tst`, version `0.14.0-dev`. No production database mutation, main push/merge, or release tag.
