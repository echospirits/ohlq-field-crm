# 0.2.2 — Bound the OHLQ intelligence refresh runtime

## Improved

- Full opportunity intelligence refreshes process up to four independent accounts concurrently, reducing the serial database work that can exhaust the 100-minute post-import budget.
- Each account's operations remain sequential and tenant-scoped. Targeted refreshes and previews retain serial execution and stable ordering.
- A failed account stops further batches after every already-started operation settles, preventing writes from being abandoned when the caller disconnects.

## Internal release manifest

- Production base: 604bd58708d52586dfc6aec84bde1a5f5457bff5 (v0.2.1).
- Observed during September 28 recovery: production's single-tenant refresh processed approximately 13,700 accounts in 59 minutes. TST has three enabled intelligence tenants under the same 100-minute budget.
- Scope: bounded execution in opportunityEngine, a small batch helper, and regressions for concurrency bounds, per-account ordering, tenant scope, deterministic previews, targeted refreshes, and failure draining.
- Scoring rules, lifecycle decisions, feature entitlements, schema, and environment configuration are unchanged. No migration or UI change.
- Validation: full tests, typecheck, builds, deployment/health, and actual recovery results are recorded in the execution evidence.
- Rollout: allow active core imports to finish. Never run two intelligence writers against the same database concurrently. The existing --intelligence-only CLI can finish a recovery with the new code without re-downloading completed reports.
- Rollback: revert this execution change to serial evaluation; no schema or data rollback is required.
