# OpenDock lookup recovery — November 9, 2026

The owner explicitly authorized this reliability correction for TST and main while retaining the current **0.7.2** version. Development remains frozen. Unrelated TST tasting features, schema changes and maintenance are excluded from production promotion.

## Incident and behavior

On November 5, 7, 8 and 9, Green's OpenDock delivery lookup returned UNAVAILABLE on the first morning run. The operational-signals failure marked the whole load failed although sales, inventory, Bailment/DC imports and intelligence completed. Later daily runs recovered the lookup. November 9 also had a separate transient database connection failure before Account Master started; this correction does not downgrade database errors.

The read-only production probe [42629937760](https://github.com/echospirits/ohlq-field-crm/actions/runs/42629937760) reproduced the cause with the existing adapter: Groveport login and availability returned HTTP 200; the immediate Green login returned HTTP 429 with Retry-After 3 seconds. The old 250/500 ms retries received 429 again (Retry-After 3 and 2 seconds) and exhausted the lookup. Honoring the server's requested wait directly addresses this recurring condition; no credential or warehouse mapping change is required.

- OpenDock retries use bounded exponential backoff, honor Retry-After seconds/dates and retain the existing three-attempt and total-time limits. A provider-requested wait beyond the remaining budget ends the lookup rather than retrying too early. Interrupted response bodies may retry; complete malformed responses still fail.
- Only UNAVAILABLE with known timeout, network, upstream-unavailable or rate-limit diagnostic codes becomes a workflow warning after its check is successfully persisted. GitHub annotations and the step summary identify the warehouse and safe diagnostic. Future CI logs retain diagnostic codes even after a successful retry overwrites the latest daily check.
- Prior successful observations remain intact; current unavailable data is unknown, not zero or an invented successful lookup. Failed locations remain eligible for the next load. Independent sources continue normally.
- Authentication failures, changed/invalid responses, unknown errors, ingestion failures and database/persistence errors remain failures. A completed search with no slots keeps its existing NO_AVAILABILITY semantics.

No dependency, version, schema/migration, provider-setting, hosted-configuration, entitlement or application-UI change is included. Existing authorization, tenant isolation, verified warehouse mappings and forecast calculations are preserved.
