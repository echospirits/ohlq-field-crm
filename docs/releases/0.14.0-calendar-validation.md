# Calendar reliability cleanup — 0.14.0-dev

Date: 2026-10-08. Scope: `neat-tst/tst` only. Daily polling unchanged.

## Changes

- Google changes reconcile before outbound recovery, including single-task saves. Only current, active assigned tasks with an exact provider/connection/calendar/event link may accept scheduling edits. Task metadata remains Neat-owned; timestamp conflict policy and conditional ETag writes are preserved.
- All calendar writers, settings cleanup and OAuth changes share a transaction-scoped advisory lock. Deferred saves remain recoverable through the next active-task/link scan. A Google-compatible random event ID is persisted before POST; retries and matching duplicate-ID recovery keep the same identity.
- Reassignment, calendar switching, pause and disconnect retain links/credentials when provider cleanup fails, preventing a replacement event from losing the old identity. Same-account reconnect preserves an unavailable linked calendar while refreshing credentials for cleanup. Different-account connection requires disconnect first.
- Explicit restoration clears removed IDs before recreating active dated tasks. Missing calendar feeds and incomplete pagination are errors; expired cursors restart safely, and failed pulls retain their cursor. Partial outbound failures are counted, not reported as success. Last-success time advances only after a complete successful check.
- Settings offer Check and sync now and Restore removed events, distinguish paused/reconnect/busy/partial/error states, explain disabled actions, announce feedback, and refresh Worklist/account views. Raw sync details use progressive disclosure. Shared mobile checkbox and pending button patterns are reused.

## Remaining live acceptance

TST calendar sync is disabled and has no connected Google accounts. Do not infer a verified end-to-end round-trip from mock tests, a healthy cron, `SYNCED`, or `lastSyncAt`. Configure only isolated TST OAuth/resources, then have a real user connect their own test Google account. Run the [manual QA](../google-calendar.md#manual-qa), especially Google reschedule → Check and sync now → matching Neat schedule, subsequent CRM edit → same Google event, reassignment, deletion/restoration and failed cleanup recovery. Deployment does not activate this integration.

Historical events with missing database links are deliberately not deleted or guessed at. Large calendars/users may need durable per-connection workers before scaling the globally serialized, bounded checks. Production promotion remains a separate release task.

Provider-safe IDs and cursor handling were checked against [Google event insertion](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) and [incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync); lock semantics against [PostgreSQL advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS).
